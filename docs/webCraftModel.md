複数の実在する一流の作り手・研究の強みを1つに合体させた、Web制作の最終思考フロー。

## ★コア1：判断駆動設計 ── 「この画面で読者が下す判断は何か」

上位1%と平均を分ける最大の一点は、技術力ではなく**削る基準を持っているか**。

```
① この画面で読者が下す判断を、1つだけ言語化する
② その判断に寄与する要素だけを表層に置く
③ 判断が変わらない要素は、深層（タップで開く）か、別画面へ
④ どちらでもない要素は、消す
```

- 「あると親切だから置く」は上位1%の判断ではない。**足す理由でなく、置き続ける理由**を要求する。
- 判断が2つ以上ある画面は、画面が2つ必要だというサイン。
- 段階的開示（Nielsen）は「隠す技術」ではなく、**表層の判断を1つに保つための道具**。
- 深層に置いてよいのは**根拠**であって、**別の結論**ではない。結論を隠すのは開示ではなく出し惜しみ。

## ★コア2：数値予算 ── 感覚で速度を語らない

プロは「速くしました」と言わない。**しきい値と実測値**で言う。

### Core Web Vitals（一次情報・2026-07-28取得）

3指標いずれも、**実ユーザーのフィールドデータの75パーセンタイル**で判定する。

|指標|測るもの|「良好」のしきい値|
|---|---|---|
|LCP（Largest Contentful Paint）|読み込み|**2.5秒以内**|
|INP（Interaction to Next Paint）|応答性|**200ミリ秒以下**|
|CLS（Cumulative Layout Shift）|視覚的安定性|**0.1以下**|

- INP は 2024年に FID を置き換えて安定版になった。FID 前提の情報は全て古い。
- **Lighthouse は INP を測定できない**（ユーザー操作が発生しないため）。ラボでは TBT が代理指標。
- 判定は CrUX（実ユーザー）。**手元の高速回線・高性能端末で速いことは、何の証明にもならない。**

### 予算の立て方

1. 対象読者の実機と回線を決める（例：数年前の中位スマホ・モバイル回線）。
2. その条件で LCP 2.5秒を満たす転送量の上限を決め、**ページごとの予算**として固定する。
3. 新機能は予算内でのみ追加する。超えるなら**何かを削ってから足す**。
4. デプロイのたびに実測し、予算超過を検出したらマージしない。

### 最適化の優先順（効果の大きい順）

```
1. 送らない        … 不要なデータ・スクリプト・フォントを消す
2. 後で送る        … 初期表示に不要なものを遅延取得する
3. 小さく送る      … 圧縮・分割・画像形式の見直し
4. 速く送る        … キャッシュ・CDN・プリロード
5. 速く処理する    … コードの最適化
```

**1と2で解決しない問題を5で解こうとするのが、平均的な作り手の典型的な誤り。**
実行時にブラウザ上でコード変換するような構成は、1の時点で失格。

## 統合：1画面を作る思考フロー

上から順に回す。これが「上位1%の頭」の中身。

1. **この画面で下す判断を1つ言語化する**（コア1）。言語化できないなら、まだ作らない。
2. **判断に寄与しない要素を全部削る**。削ってから足す。
3. **表層／深層を切り分ける**（Nielsen）。基準は「無くても今日の判断ができるか」。
4. **数字は比較できる形にする**（Tufte）。単独の数字は意味を持たない。母数・分布・前回との差を同じ視野に入れる。
5. **装飾のインクを削る**（Tufte）。枠線・影・グラデーション・3Dは、理解に寄与しない限り全て削る。
6. **同型のものは同一スケールで並べる**（スモールマルチプル）。個別に凝った図を並べるより比較が速い。
7. **図の型は「伝えたい関係」から選ぶ**（FT Visual Vocabulary）。時系列／比較／構成比／相関／分布で型が決まる。棒と折れ線を惰性で選ばない。
8. **考えさせない導線にする**（Krug）。現在地・戻り方・次の一手が、読まなくても分かるか。
9. **予算内に収める**（コア2）。転送量・スクリプト依存・実行時処理を数値で確認する。
10. **視覚的に安定させる**。後から高さが変わる要素に寸法を予約する（CLS）。読んでいる最中に文字が動くサイトは信用されない。
11. **再訪の理由を、煽らずに作る**。定時更新・更新時刻の明示・URLで共有できること。可変報酬と通知には頼らない。
12. **全員が使える形にする**（WCAG）。タップ対象・コントラスト・色以外の手がかり・キーボード操作。
13. **実機で測る**。PCのラボ値でなく、対象読者の実機・実回線で読む。
14. **正本と生成物を構造で分ける**。人間の記憶で管理しない。

## 日本語Webの固有要件（JLReq）

欧文の常識をそのまま持ち込まない。

- 日本語は**単語間スペースが無い**。行長と禁則処理が読み速度を直接決める。
- 行長が長いと次行の頭を見失い、短いと視線移動が増える。**実機のスクリーンショットで1行の文字数を数えて決める**。ネットの一般論を借りない。
- 行間は欧文より広く要る。数値は実機で読んで決める。
- 和欧混植（日本語と数字の混在）は間隔の調整が要る。データを扱う画面では特に効く。
- 数字は等幅数字（`tabular-nums`）で桁を揃える。**桁がずれた表は比較できない＝表の意味が消える**。
- 固有名詞（人名等）を途中で改行させない。
- iOS Safari は文字サイズ16px未満の入力欄で自動ズームする。本文16px以上を基本にする。

## アクセシビリティの最低ライン（WCAG 2.2・一次情報）

WCAG 2.2 は **2023年10月5日に W3C 勧告**。2.1 から9つの達成基準を追加し、4.1.1 Parsing を廃止。

|達成基準|要件|
|---|---|
|2.5.8 ターゲットサイズ（最小）AA|ポインタ操作の対象は **24×24 CSSピクセル以上**。小さい場合は、各対象を中心とする直径24pxの円が他と重ならない間隔を確保|
|1.4.3 コントラスト（最小）AA|通常テキスト **4.5:1** 以上、大きいテキスト **3:1** 以上|
|2.4.11 フォーカスの非隠蔽（最小）AA|キーボードフォーカスを受けた要素が、固定ヘッダー等で完全に隠れてはならない|
|2.5.7 ドラッグ動作 AA|ドラッグで行う操作には、ドラッグ以外の手段を用意する|
|3.2.6 一貫したヘルプ A|複数ページに繰り返すヘルプは、同じ相対位置に置く|

さらに、色に関する原則：

- **色だけで情報を伝えない**。色に加えて、記号・文字・形のいずれかを併記する。
- 1つの色に意味は1つだけ割り当てる。色の意味が2つ以上あるサイトは読めない。
- 見た目を変えずに当たり判定だけ広げられる（`padding` の活用）。小さいボタンは見た目の問題ではなく、押し間違いの問題。

## 否定側 ── 上位1%が採用しない手法

技術ではなく倫理で線を引く。Brignull の分類でいう欺瞞的パターンは全面的に不採用とする。

|やらない|理由|
|---|---|
|ストリーク（連続訪問記録）・カウントダウン|訪問を義務化し、離脱に罪悪感を与える|
|可変報酬（ランダムな当たり演出）|射幸心の設計そのもの|
|プッシュ通知による行動の急かし|読者の時間を奪う設計|
|数字のカウントアップ演出|数値を演出物にする。実数の重みが下がる|
|無限スクロール|現在地を失わせ、視覚的安定性も壊す|
|同意を得るための誘導（拒否を遠回りにする）|信頼を一度で失う|
|「あなただけ」「残りわずか」型の煽り|判断でなく反射を誘う|
|飾りのためのアニメーション|理解に寄与しないインク。処理も遅らせる|

**線引きの原則：読者の判断を助けるものは採用し、読者の反射を利用するものは採用しない。**

## ビルド構造 ── 事故を構造で防ぐ

- 正本（source of truth）と生成物を**人間の記憶で管理しない**。生成物には自動生成である旨を機械挿入する。
- 同じ値が2箇所以上に書かれている時点で、いつか食い違う。定数は1箇所に集約する。
- 生成物の手編集は、CIで再生成して差分検出し、失敗させる。
- 完了報告でなく**生成物の実物**を照合して検収する。

## 監査チェックリスト（全実装の受け入れ基準）

1. この画面で下す判断を1つ言えるか。
2. 新しく足した要素は、その判断に寄与するか。しないなら深層か削除。
3. 数字に母数・出典・比較対象があるか。単独の数字を置いていないか。
4. 色を増やしていないか。1色1意味を守っているか。色だけで伝えていないか。
5. 初期表示の転送量は予算内か。初期表示に不要なものを載せていないか。
6. 実行時にブラウザ上でコード変換していないか。
7. 後から高さが変わる要素に寸法を予約したか。
8. 実機（対象読者の端末・回線）で読んだか。1行の文字数と行間を確認したか。
9. タップ対象は24×24px以上か。コントラストは4.5:1以上か。
10. 煽り・射幸心・欺瞞的パターンが混入していないか。
11. 正本を直したか。定数を二重に書いていないか。
